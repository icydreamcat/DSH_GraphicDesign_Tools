# 视觉设计通用方法原理（给 agent 用）

> 这份文档不是理论综述，是一份**可执行的工作协议**。
> 每条规则都带：**判据**（怎么算做到了）、**阈值**（数字是多少）、**失败模式**（不做会怎样）。
> 所有数字来自一次真实拆解的实测（《明日方舟：终末地》视觉语言分析），它们是**锚点范围**，不是必须复刻的目标值。
>
> 使用方式：开工前读完第 0–3 节（这是顺序，跳过任何一条都会在后面付出重建的代价）；做具体设计时按第 4–10 节；交付前过第 11–13 节。

---

## 0. 一切错误的总源头：从第四层开始做

设计有四个层级，**它们有必须遵守的顺序**。从第四层开始，前三层就不可挽回了——因为等你发现层级错了，每个元素都已经摆好、定了尺寸。

| 层 | 问题 | 听起来像什么 |
| --- | --- | --- |
| **1. 功能** | 这个版面必须完成什么？ | "读者必须在三秒内知道这是什么。" |
| **2. 层级** | 什么最重要，眼睛按什么顺序走？ | "标题是唯一的 A 级。名字是 B 级。其余全是注释。" |
| **3. 关系** | 比例、重量、位置、间距是多少？ | "标题是次级的 2.4 倍，占版心的 38%。" |
| **4. 形式** | 用什么形状、颜色、字体？ | "低彩度橄榄绿、描边无衬线、24px 模数。" |

**美学活在第三层，不在第四层。** 真实失败记录里，六个错误全部是**关系性**的，没有一个错在"颜色不好看"或"形状不美"：

| 做成了 | 应该是 | 错误类型 |
| --- | --- | --- |
| 主体占画布高度 90% | 约 60%，留呼吸空间 | **比例** |
| 几何块不透明且巨大 | 小、极淡、成层 | **重量** |
| 24px 网格铺满全画布 | 稀疏、有选择、成系统 | **密度** |
| 名字用实心白压在浅底上 | 橄榄描边，且是视觉主导 | **顺序** |
| 半调网点做满版背景 | 调性工具，局部出现 | **材料理解** |
| 主要信息（名字）被次要信息（职业）压过 | 清晰的一级与二级 | **层级** |

**当作品看着业余时，先看关系，几乎总是在看元素之前。**

## 1. 开工前必须写下的三句话

在放置任何元素之前，用文字写下：

1. **读者第一眼必须看到什么，而且只有那一个。** 不是"看到标题"，是"看到 X，且不与任何其他元素争夺"。
2. **眼睛的路径。** 从哪开始，经过哪，停在哪。
3. **哪些元素是次要的、必须让位。** 让位意味着更小、更淡、更靠边——不是"也还行"。

**没写下这三句就开始摆形状，是装饰，无论手法多熟练。** 这一步的缺失事后最不可见，代价最大。

---

## 2. 每定一个值，同时写下它相对什么

对比是**对什么**的对比。比例是**对什么**的比例。

- ❌ "标题是 148px" —— 没有信息。
- ✅ "标题是次级的 2.4 倍，占版心 38%" —— 这是决策。

**强制动作：任何色值、尺寸、间距，都必须在同一行写下它落在哪个面上、与谁成比例。**

原因不是形式主义。实测证据：同一个黄 `#FFFA00` 在深色底上对比度 15.26:1，在奶油纸底上 **1.07:1**——**等于抹除**。同一个 token 因为落在不同面上，一次是强调，一次是看不见。**"底色归一套、文字归另一套"就是裂缝。**

## 3. 测量，不要估计

你有返回真实数字的工具。用它们，而不是推理"大概是多少"。

| 问题 | 工具 | 读哪个字段 |
| --- | --- | --- |
| 底色是什么？ | `design_analyze` | `tone.groundHex` / `groundLuminance` |
| 调性带有多宽？ | `design_analyze` | `tone.p05/p50/p95`、`dynamicRange`、`histogram` |
| 强调色占多少？ | `design_analyze` | **`accent.flatShare`**（不是 `share`） |
| 有网格吗？ | `design_analyze` | `grid.columnPitch` + `columnStrength` |
| 元素多不多、淡不淡？ | `design_analyze` | `structure.elementCount`、`regions[].impliedOpacity` |
| 线有多细？ | `design_analyze` | `strokeWeights[]`、`hairlineShare` |
| 细节在哪里？ | `design_analyze` | **`spatial.cells[].detail`**（最常被跳过、最常决定成败） |
| 字号真有多大？ | 见 3.2 | 逐行墨量 |
| 正文真有多宽？ | 见 3.2 | 逐行墨量 |
| 版面上一个元件有多淡？ | `design_critique` / `design_verify` | `accentFlatShare`、`meanOpacity`、`heavyShare` |

**测量工具的输出永远是规格的起点，不是终点。** 一个测出来的值，要能回答"它相对什么"。

### 3.1 描述 vs 规格

```
描述（无用）：
  "这个参考有半调网点、橄榄绿、几何元素和等宽标签。"
  —— 无法据以建造，而"抄一个观感"恰恰就是由这种句子构成的。

规格（可建造）：
  "底色亮度 0.84（#EBEBEB）；容纳 90% 像素的调性带跨 0.78，集中在底色附近；
   强调色 3.1%，按大块平涂计；主色是占比 1.1% 的浅奶油与合计 2.6% 的橄榄家族；
   35px 列网格，置信度 0.74，行网格未解出；主导线宽 1px（59%）与 2px（33%）；
   解出 27 个区域，从画布的 0.1% 到 4%；局部细节在图元区峰值 0.061，
   在底色角落降到 0.001。"
  —— 可建造，且事后可核对。
```

### 3.2 字号的真实测法（不要目测）

用逐行墨量扫描，而不是看截图估：

```
对给定矩形，逐 y 统计"亮于阈值"（浅字压深底）或"暗于阈值"（深字压浅底）的像素数。
墨迹带的行数 ≈ 字面高度；CJK 字面约占 em 的 0.88，数字高约占 0.72。
```

实测得到的三级（原生 2560×1600 画布）：**正文 25px 墨迹 → 字号 ≈28px；按钮标签 26px → ≈30px；展示数字 49px（数字高）→ ≈68px。**

行长同理：找该行最左与最右的墨迹 x，得真实版心宽度。实测 1285px，按 28px 字号计 **≈46 汉字/行**——**已超出中文舒适区（25–40）上沿**。

## 4. 分层：深度轴（本文最重要的一节）

### 4.1 你的分析框架必须先有深度轴

面积占比、元素数量、线宽分布、对比度、留白比例——**全是平面上的量。它们没有深度。**

一个真实教训：我测到某块面板的"隐含不透明度 0.33–0.46"，据此写下"大块也是淡的"，并定了"元素要多、要淡"这条处方。**录像推翻了它**：那个"淡"不是设计决策，是**四层叠合后的合成结果**。我把一个**堆叠结构**读成了平面上的**低对比决策**。

**判据：如果你描述一个元件时只能说它的面积和对比度，你说不出它的层位，你就还没有分析完。**

### 4.2 实测的深度结构（四层，每层一种职务）

| 层 | 实测值 | 职务 |
| --- | --- | --- |
| 底 | 近黑，≈42% 像素落在最暗档 | 压住背景（3D 场景 / 图像），让界面退后 |
| 承载面 | `#2B2929` | 列表、实时数据、状态读数 |
| 可操作面 | `#C3C3BF`–`#CDCBCB` | 按钮、可点击区域 |
| 焦点层 | `#FDFCFC` | 唯一焦点，**反相** |

**规则：3–4 层，每层一种职务，不要更多。** 层多了就没有层位可言。

### 4.3 焦点靠反相，且一次只留一个

实测：屏幕上最亮的那一个元件（`#FDFCFC` 面板，压在深色 HUD 上）既不是最大的，也不是对比最高的，也不在视觉重心上。它是**唯一翻转了明暗语域**的元件。

- 这比加边框、加投影、放大、加动效都**便宜**。
- **代价明确：用第二个就不成立。** 两个反相元件等于没有反相。

**判据：数一下这一屏有几个"翻转语域"的元件。必须是 1。**

### 4.4 分层 ≠ 半透明

实测：两条 HUD 胶囊**都是不透明的**（α ≥ 0.942 与 α ≥ 0.997）。

**该保证可读性的地方，不要让底透过来。** 这与流行的毛玻璃方向相反，而且是个可测的取舍：用"失去世界感"换"阅读稳定"。

**判据：需要被读的数据，其承载面必须不透明或近乎不透明（α ≥ 0.9）。**

### 4.5 深度与密度是连着的（这条修正了"高频低对比"）

**"元素要多、要淡"是一条不完整的处方——它给了密度，没给结构。**

- 在一个平面上撒一百个 6% 的记号是**糊**。
- 把它们分布到四个深度层上才读成**系统**。

**正确顺序：先定层，再定密度。**

### 4.6 分层的代价（必须写进交付）

**分层是屏幕原生手法，印刷与单色下会崩。**

实测：`#2B2929` 压在近黑底上，对比度仅 **1.144:1**。它的"可见"完全依赖底可控。

> **原则：凡是靠明度差建立的结构，都要问一句"它在灰度下还剩多少"。**
> 靠形状、位置、字号建立的结构能活过打印；靠明度差建立的不一定。

**同一物理原因的另一个观测：** 深色底上的线要更细（1px 主导，占 38%–55%），浅色纸上的线要更重（2px 多于 1px，34.7% vs 27.5%）。近黑底上 1px 亮线已足够可见；亮纸上 1px 会消失。

## 5. 高频低对比：完整版

原始规则是对的，但不完整。完整版：

> **要素很多，每个都很淡；而"淡"必须由分层供养。**

- 一个繁忙的页面不等于一个吵闹的页面。一百条 6% 不透明度的发丝线读成**精细**；五个 60% 的色块读成**粗笨**。
- **"为了给它存在感而把它变大、变深、变更不透明" —— 这个冲动是错的。** 正确做法是在它周围加更多更小的元素，或者给它留空间。

**可测的目标区间（实测锚点）：**

| 指标 | 区间 |
| --- | --- |
| 独立区域数 | **40 个以上**（细密页可达 300） |
| 单个最大区域占画布 | **≤ 15%** |
| 1px 线占比 | 深色面 **38%–55%**；浅色面 2px 反超 |
| 局部细节峰值 / 最低值 | 相差 **5–8 倍**（必须局部化，不能均匀） |

**细节必须局部化。** 实测：同一张主视觉，中部细节 0.079，底部两角 0.010——相差近 8 倍。均匀铺满的纹理读成"壁纸"，局部出现的纹理读成"制图"。

### 5.1 面积占比相同 ≠ 设计相同（一条被实测确立的规则）

**这是最容易犯、也最难自己发现的一条。**

一个区域占了画布的 42%，于是你也放一个占 42% 的色块。**占比对上了，但别人那 42% 不是一块色，是一整片有内部层级的编排。** 你用填充替代了编排。

**"填满"不是"留白"，"占比正确"不是"设计正确"。**

#### 度量方法

取该区域的矩形，统计两件事：

```
主导平涂色占比 = 出现次数最多的那个 RGB 占该矩形的比例
可分辨色数     = 该矩形内出现的不同 RGB 个数
```

#### 判据（实测区间，取自参考的 UI 表面）

| 指标 | 合格线 |
| --- | --- |
| 大区域主导平涂色占比 | **< 25%**（参考 UI 表面实测 3.0%–20.8%） |
| 大区域可分辨色数 | **200–7000**（视区域职务：安静的承载面 188–200，最丰富的制图底 1383–7032） |

实测对照：

| 取样 | 主导平涂 | 可分辨色数 |
| --- | --- | --- |
| 参考：主界面左缘 UI 底 | **3.0%** | **1383** |
| 参考：主界面右下 UI 底 | 20.8% | 196 |
| 参考：邮箱空面板 | 19.6% | 188 |
| 参考：背包下面板 | 14.5% | 7032 |
| **不合格**：我自己的封面底（修前） | **42.8%** | **327** |
| **不合格**：我自己的浅色面板（修前） | **87.6%** | **191** |
| 修后：封面底 | 3.5% | 234 |
| 修后：焦点面板 | 29.0% | 417 |

**修前那两块是标准的"一个方块代替一整片设计"：占比没问题，设计性为零。**

#### 整页口径（更稳，不依赖手工挑取样块）

手工挑取样块极易挑错地方——我连续两次把取样点落进了色卡和面板里，还拿 UI 底去比了画面内容。**整页统计不需要你猜**：

| 取样 | 主导平涂 | 可分辨色数 |
| --- | --- | --- |
| 参考 ui-12 百科（纸面页） | 10.1% | **1022** |
| 参考 ui-16 邮箱 | 10.1% | **6665** |
| 参考 ui-03 主界面 | 11.2% | **18071** |
| 我的 10 页（修后） | **2.9%–5.4%**（P2 31.8%、P6 33.7%） | **489–928** |

**读法：**
- **主导平涂低于参考** → "一个大方块"的病治好了，页面上没有任何一种色占主导。
- **可分辨色数仍低 1–7 倍** → 但参考的高色数里有相当一部分是**媒介**带来的（3D 渲染、透明面板后面的摄影世界、抗锯齿的多字号文字），不是设计手法。**把色数当成目标去追，就会开始伪造一个自己并不在的媒介。**
- **注意 ui-03 的 18071 主要来自表盘内的地形渲染**（画面内容），不是 UI 底。**目标不要取它。**

#### P2 的 31.8% 不是缺陷，是构图后果

那半页浅色纸占画布 48.9%。参考的纸面页之所以能压到 10.1%，是因为它被六个大图元、一排幽灵数字和一条刻度尺破开了；而那一页的**功能**是索引。**当"再丰富一点"意味着"改成另一页"时，就该停手。**

**判据：先问这个区域的职务，再问它的主导平涂。** 一块安静的大纸可能是对的；一块本该承载信息的安静大色块一定是错的。

#### 一条会静默毁掉整页的单位陷阱

**在这个引擎里，长度 ≤1 是画布比例，>1 才是像素。**

```js
rect(x, y, 1, 1, '#0F1213')   // 想做 1px 斑点
// 实际得到：一个铺满整幅画布的不透明矩形（1 = 100%）
```

我写了 300 个"斑点"，其中 200 个是满幅覆盖，**把整页底色冲成灰色，主导平涂从 3.5% 飙到 54.4%、可分辨色数从 234 掉到 118，而引擎零报错。**

**防护动作：任何"1px 的点"都必须写 ≥2。** 并且渲染完必须跑一次整页统计——这类错误在缩略图上看起来只是"有点脏"。

---

#### 类别警告（我犯过的错，写下来防再犯）

**只能拿 UI 表面比 UI 表面，绝不能拿 UI 表面去比画面内容。**

我第一次对比时，取了自己版面的底面去比参考里**表盘内的地形渲染**（2926 色），得出"少 9 倍设计"的结论——**那是画面内容，不是 UI 底色。** 换成真正的 UI 底色后，参考区间是 188–7032，我的 234/417 落在区间内。

**先确认你量的那块在参考里是"设计的表面"还是"呈现的内容"。** 这是同一类错误：比错了对象。

#### 补细节的三个手段（按成本排序）

1. **亚阈值颗粒。** 一个 `noise` 源 + `blend`，极低 amount。
   ⚠️ **陷阱：** 现成的 `filmGrain` 预设用 `luminanceMask` 把颗粒限制在**中间调**——套到近黑底上遮罩值≈0，**等于没做**。要自己写图，去掉那个遮罩。
2. **细横纹。** 参考的纸面实测有强横向线结构（`rowStrength` 0.915，14px 周期）。十几条 1px 发丝线，对比度压到 1.06–1.1:1。
3. **斑点场。** 1–2px 的小点，比底亮一档、暗一档交替。这是最便宜的"可分辨色数"来源。

#### 但细节 ≠ 层级

**颗粒给的是细节，不是层级。** 层级必须靠区域内部的**信息编排**：

- 一个 1px 的顶边高光（"这是一块被照亮的实体"）
- 四角对位括号（"这是被框定的一栏"）
- 一行拉丁微标签 + 一条发丝线（"这一栏有名字"）
- 内部文字的三级重量（标签 / 值 / 单位）
- 一处局部渐隐（"纹理在这里出现又消失"，而不是均匀铺满）

**判据：把这块区域的文字全部删掉，它是否仍然读起来像"一块被设计过的面板"而不是"一个色块"？** 如果只像色块，你缺的是上述五条中的某几条。

## 6. 色彩：预算、语义、落点

### 6.1 强调色是预算，不是偏好

- 度量口径：**`flatShare`**（属于未被中断的大面积平涂的彩色像素），不是 `share`（含插画在内的全部彩色像素）。
- **实测区间：大块平涂 0%–2%，特例 3.1%；色相存在感（含细线、发光、小徽标）3%–5.5%。**
- 10% 就不是强调色了，是一个色块场。

**`flatShare` 的三个陷阱（都会让你读错）：**
1. **自发光会系统性低估。** 某屏实测 `flatShare` = 0，但该屏确实充满黄色——因为黄以发射光形式存在，边缘柔和，不构成平涂。**自发光为主的界面上必须同时看色相簇占比。**
2. **它测的是"平涂存活量"，不是"设计的强调色面积"。** 一条满幅黄带被字标和辉光打断后，`flatShare` 只有 1.0%，而色相簇是 4.55%。
3. **它不会告诉你平面和分层的区别。** 见第 8 节。

### 6.2 语义分工：不同用途的颜色不能互换

实测的一组分工：

| 色 | 用途 | 纪律 |
| --- | --- | --- |
| 黄 `#FFFA00` | **品牌信号**：数值、状态、激活、物的流向 | 唯一强调色，大块平涂 ≤2% |
| 橙 `#FF7500` | **新 / 未读 / 待处理标记** | 只做标记，不做底色 |
| 红 `#840000` 系 | **紧急徽标** | 只做徽标 |
| 绿 / 洋红 | 状态（正常 / 异常） | 用量低于黄的 1/4 |

**三者不可互换。** 用黄去做"未读标记"，或用橙去做主信号，都会让整套纪律失效。

### 6.3 信号色应该来自世界里本来就有的东西

最聪明的一处实测：界面的信号黄，与世界里的花、产线的辉光、设备的警示条**同属一个色相家族**。所以界面上的黄读起来像"从这个世界取来的信号"，而不是贴上去的图层。

> **可执行：先在世界美术（或素材库）里确立信号色，再让 UI 使用它。** 不是先定 UI 主色，然后去世界里找补。
> 反例（常见失败）：从色板里挑一个高饱和黄刷到界面上——得到一块塑料板。

### 6.4 底色规则

- **不用纯白。** 暖白（`#F1F1EC`）读成纸；`#FFFFFF` 读成屏幕。
- **不用纯黑。** 用带一点色偏的近黑（`#191919`、`#0A0B0C`）。纯黑是"未设定"。
- **底色渐变要几乎看不见。** 两三档、极短范围。看得见的底色渐变是另一种设计。
- **给底色一个局部事件，不是一个均匀事件。**

## 7. 排版：三类角色 + 一条反阶梯

### 7.1 三类文字角色

| 角色 | 字面 | 字重 | 大小写 | 字距 |
| --- | --- | --- | --- | --- |
| **展示字** | 宽体 | UltraBold / Black | 全大写（拉丁） | **-0.02 ~ -0.04em**（收紧） |
| **正文** | 常规 | Regular / Medium | 句首大写 | 0 |
| **技术标注** | 等宽 or 常规 | Regular | **全大写** | **+0.10 ~ +0.20em**（打开） |

**字距的正反不是装饰，是光学间距。** 大字号时字体内建边距看起来像缝，要收紧；小字号需要空气才分得开，要打开。

### 7.2 界面层不要用连续比例阶梯

实测：某游戏界面的字号是 **28 / 30 / 68px**。相邻比 **1.07×** 与 **2.27×**。

**这不是比例阶梯，是"一段很窄的文本带 + 一次大幅跳升的展示层"。**

- 连续阶梯（16 基、比例 1.25：16/20/24/32/40/48）属于**网页与传播物料层**。
- 界面层要的是：文本挤在窄带内（避免层级碎片化），然后给展示层一次大幅跳升。

**判据：算一下相邻两级之比。如果所有相邻比都在 1.2 附近，你可能在做网页而不是在做界面。**

### 7.3 行长与行距

- 拉丁：**45–75 字符/行**，60–70 最佳。
- 中文：**25–40 字/行**（每个字一个全角）。实测 46 字/行偏长——**这是真实取舍**：宽屏面板优先填满宽度，代价是回扫距离。
- 行距随行长上升：40 字版心 1.4 舒适；80 字版心需要 1.5–1.6。
- 小的正文用更松的 leading（1.6），正文 1.5，小标题 1.3，展示字 1.08。

### 7.4 混排脚本：必须用字体栈，并检查有没有豆腐块

- CJK 与拉丁混排时，用**字体栈**，让引擎把字符串按脚本拆开，每段给第一个覆盖它的字族。
- **把静默 fallback 当作缺陷处理。**
- **实测陷阱：** 某等宽字族（Cascadia Mono）与某 DIN 血统字族（Bahnschrift）的 `scripts` 只有 `latn`。把中文塞进去会渲染成**满屏豆腐块（□□□），而引擎不报任何警告**。**必须在写文字层之前检查字族的脚本覆盖范围。**
- **另一个实测陷阱：** 变量字体通过字体简写里的 weight token **不生效**。某可变 CJK 字族的默认字重是 100，用错不会得到"正常字重"，会得到**发丝线**——看起来像一个刻意的风格选择，非常容易误交。字重必须走 variation axis，或直接用静态字重实例。

## 8. 单帧的边界：分层效应会污染五个指标

**一张截图不是平面，是一次合成。** 用平面指标去读分层设计，会得到"自信的错答案"。

| 分层机制 | 为什么破坏平面测量 | 污染的指标 | 判据（怎么检出） |
| --- | --- | --- | --- |
| **① 半透明合成** | 读数 = α·元件 + (1−α)·背景。**"中灰不透明面板"与"深底上的半透明白面板"在单帧里数学上不可区分** | 一切"不透明度"读数、跨区域色调比较 | **固定元件、变动背景，看读数动不动** |
| **② 自发光 / 辉光** | 边缘柔和，不形成平涂区域；辉光细丝还会制造 1px 游程 | `flatShare`（系统性低估）、发光元素面积、笔画游程 | 找同一元素在无辉光状态下的样子 |
| **③ 全局后处理**（渐晕／色彩分级／颗粒／景深／锐化） | 同一个色板 token 在屏幕不同位置读出不同值 | 跨位置颜色比较、空间细节分布 | **同一元件在屏幕不同位置取样** |
| **④ 信箱黑边** | 常数污染 | 直方图、最暗档占比、均值亮度、覆盖黑边的空间格 | **先测黑边，再剔除，再做任何整帧统计** |
| **⑤ 遮挡顺序** | 你以为在测 A 层，实际测的是压在上面的 B 层 | 任何按包围盒求平均得到的颜色 | 1:1 切开看 |

### 8.1 三个实测案例（照做即可复现）

**案例一 · 固定元件、变动背景（判决性）**

同一个状态胶囊出现在两段素材里，背景亮度一个约 0.10（近黑），另一个在同一帧内从 0.317 到 0.994（含近纯白）。

| | 背景 | 胶囊填充（逐列模态色） |
| --- | --- | --- |
| 素材 A | 近黑，亮度 ≈0.10 | (42,40,40) – (49,47,47) |
| 素材 B | 同帧内 0.317 → 0.994 | (42,41,43) – (43,42,44) |

**背景亮度差最高 0.9，胶囊填充只动 ≤7/255（≤2.7%）→ 不透明。**

**案例二 · 同一元件在屏幕不同位置（渐晕的存在证据）**

四个**同款**按钮，填充实测单调递减：**205 → 199 → 197 → 195**（差 10/255）。

四个按钮设计相同，背景不同 → **屏幕上存在一层全局渐晕**。**结论：任何"某面板的填充色是 X"的陈述，必须加限定——它在屏幕上下两端可以差 4%。**

**案例三 · 纸上的实心色带**

一条满幅实心黄带，在纯色区 R−G ≈ **+8**；靠近插画边缘处 R−G ≈ **−3 至 −5**。**色相在带内翻转了**——因为边缘有辉光/扩散层在渗。

**这解释了一个常见的读数错误：** `flatColors` 报出"两个不同的黄"（`#FAF139` 与 `#F9EF3D`），它们**不是两个色板值，是同一条带在不同底上的两种合成结果**。

### 8.2 由此被修正的结论（保留作警示）

| 错误结论 | 修正后 |
| --- | --- |
| "大块的隐含不透明度 0.33–0.46，所以大块也是淡的" | 只成立为**合成后亮度覆盖**；**不能读作设计不透明度** |
| "最暗档从 48.1% 到 48.0%，四年完全未变" | **错**。剔除 10% 信箱黑边后是 48.1% → **≈42%**，差 6 个百分点 |
| "`flatShare` = 强调色预算" | 它测的是**平涂存活量**，不是设计面积 |
| "`columnPitch: null` 说明没有网格" | **错**。检测器找的是"画出来的线"，不是"平铺的格子"。一个视觉上明确的瓦片网格同样报 null。**null 只能读作"未检出"，不能读作"不存在"** |

### 8.3 一条通用规则

> **做任何拆解时，每个数字都要标注它是"合成值"还是"设计值"。**
> 合成值可以比较、可以定位、可以作为规格的**约束**；但一旦你把合成值当成设计值写进规范（例如"大块不透明度 ≤0.5"），你就是在照着别人的显示器校准自己的画布。

## 9. 什么时候必须让画面动起来

**单帧能做的：** 颜色、比例、密度、网格、字号、层位。
**单帧做不到的：** 半透明判定、动效参数、状态转场、以及"哪些元素是真的一层"。

### 9.1 判别实验：用回归解出 α

模型：

```
rendered = α·F + (1−α)·B
```

`F` 是元件自身颜色（常数），`B` 是背景（变化）。对背景做回归：

```
斜率 s = 1 − α   →   α = 1 − s
截距 c = α·F     →   F = c / α
```

**关键性质：线性色调缩放（如 limited→full range 转换）会在斜率里约掉，所以 α 对它是免疫的。非线性调色（滤镜、HDR 转换）不免疫，会引入偏置。**

### 9.2 两个统计量，各自的成立前提不同

| 结论 | 用哪个统计量 | 前提 |
| --- | --- | --- |
| **不透明** | **方差比 σ(元件)/σ(背景)** | **不需要相关性。** "这个不动而那个在动"本身就是正面证据 |
| **半透明（并给出数值）** | **回归斜率** | 需要背景代理跟得准（R² 高） |

**这是一个真实的 bug 教训：** 我一开始用斜率判"不透明"。实拍素材有噪声，噪声对上大幅变化的背景会回归出一个**假的非零斜率**（0.45，R²=0.37），于是把明明不透明的元件误报成"无法判定"。**判"它不动"根本不需要相关性——用方差比。**

### 9.3 取样纪律

- **背景取样块要放在元件的正上方或正下方。** 镜头水平平移时，垂直偏移在同一时刻看到的是同一段世界内容，相关性最高；水平偏移会取到时间错位的内容。
- **元件 ROI 里可以有文字和图标。** 它们随时间不变，只会改变反推出的 `F`，**不影响斜率**。所以 ROI 可以放宽，但**绝不能漏进未被遮挡的世界**（那会混入 α=0 的成分，把 α 拉低）。
- **先分段，再回归。** 真实录像永远不是"一段"。实测教训：一段 20 秒素材在中途整块切换了 UI 布局，两段混在一起得到"方差比 0.733、α≈0.27"这样一个**自信的错答案**；分段之后同一素材给出正确的 α ≥ 0.942。
  **流程：先做帧间差分找切换点 → 选出稳定段 → 才做回归。**
- **该拒绝时必须拒绝。** 背景激励不足、或拟合 R² 过低时，输出"无法判定"并说明原因，**不要给一个数**。

### 9.4 编码偏置（量化过）

同一素材编成 H.264 后重测：

| 编码 | 实测 α（真值 0.50） | 偏置 |
| --- | --- | --- |
| crf 18（近乎无损） | 0.481 | −0.019 |
| crf 30（重度压缩） | 0.490 | −0.010 |

**偏置是 ±0.02 量级的散度，不是系统性偏移**（更差的编码反而更准）。**所以录像不需要无损。**

## 10. 素材纪律

### 10.1 真实素材 > 生成几何 > 通用图标包

- **真实素材**带来遮挡、叠压、细枝结构，这是递归几何追不上的。
- **但前提是主体正确。** 一张主体错误的真实照片，比一张主体正确的画更糟。**主体是否决权，不是技术。**
- **通用图标包只能提供形状，不能提供词汇。** 实测：一个 177 张的通用工业标记包，改色后放到 52px，**读起来就是一个方框**，与画出来的矩形无法区分，还挤到了旁边的编号标签。
  **记号（mark）的本质是"位置"或"状态"，不是轮廓。**

### 10.2 素材只能被画出来或被重构，不能被粘贴

一个复制来的形状不携带**解剖结构**，所以它无法被旋转到另一个姿态——任何角度下它都读成同一个剪贴件。**重构意味着用它自己的部件重建它，这样部件才能各自独立运动。**

### 10.3 替换素材 = 在同一次改动里删掉旧素材

只加不删会留下**两代同堂**，而旧的那一代通常正是上一轮否掉的方案。**半替换的页面，在看过上一轮的人眼里是倒退，不是进展。**

### 10.4 生成规则胜过一百次摆放

**逐一摆放元素而不给出生成它们的规则，得到的是一页"排得整齐的陌生人"**——每个元素单独看都没问题，但没有一个在回应另一个。

**检验很便宜：说出生成这一组的规则。**
- ✅ "这些记号沿视线方向依次退出，越远越小越淡。"
- ❌ "我看着好就放那儿了。"

**另一条：图元由基元拼装，角点吸附到网格交点。** 实测：某百科页的六个图元不是插画，是**矩形 + 圆 + 菱形**拼的，且每个基元的角点、圆心都落在方格网的交点上。这解释了它们为什么"像工程符号而不像图标"。**这是一条生成规则，照做时先定网格，再把基元吸附上去。**

### 10.5 记号分两类，不可互换

| 类型 | 特征 | 价值在 | 用法 |
| --- | --- | --- | --- |
| **标记 marker** | 径向对称，无轴线 | **位置** | 四个标记定义一个矩形，眼睛把围出的区域读成一个整体 → **放四角，不要散落**。散落就毁掉了它唯一的用处 |
| **指针 pointer** | 有头有尾 | **描出的路径** | 沿阅读方向排列；位置只是路径上的一个点 |

**记号绝不能与字标竞争。** 用**组不透明度 + 尺寸比**压住它，而尺寸比是最常被忘的那一半：32px 的记号对 218px 的字标是 **1:7**，这个比例才是让它们读成"场"而不是"小竞争者"的原因。**只降不透明度，它们仍然是竞争者。**

### 10.6 差异是机制，不是修饰

**一页完全相同的记号、相同重量，是纹理，而纹理没有方向。**

运动需要**沿眼睛行进的方向**变化，而且三个轴要同时变：**哪个记号、多少个、多重**。只变大小，纹理依然是平的——更大的相同记号还是相同记号。

## 11. 两件容易被误读的事

### 11.1 一个"很淡"的元素可能只是一个结构

见第 4、8 节。**"要淡"是不完整的处方；正确顺序是"先定层，再定密度"。**

### 11.2 照片是体块，不是纹理

**字落在照片让出的空间里，而不是压在它上面。**

把文字块放在一个照片体块的中间，是页面"每一项测量都通过、但可读性已经死了"的最常见原因——对比度检查测的是文字下方的**平均**值，平均值可以很舒服，而逐个像素不是。

## 12. 交付前检查清单

### 12.1 四个问题（两个可测，两个要你自己诚实回答）

1. **删掉一半元素，信息还完整吗？** 如果删掉一半不损失任何东西，那一半就是装饰。**构图不成立时，第一个动作是减，不是加。**
2. **眯眼看，焦点唯一吗？** 多个焦点等于没有焦点。**这是缺陷，不是警告。**
3. **去掉颜色，层级还成立吗？** 靠颜色承载的层级是最脆弱的：单色印刷、灰度、以及不区分那些色相的读者，都会让它消失。**层级必须由大小、字重、位置承载；颜色是放大，不是结构。**
4. **忽略内容，这个版面传达了性格吗？** 有性格 = 有可测的网格 + 一致的线宽词汇 + 受控的调性带，与文字内容无关。

### 12.2 机器可查的项

```
design_verify  <scene.json> --png <render.png>
design_critique <render.png>
```

读这些字段：

| 字段 | 合格线 |
| --- | --- |
| `accentFlatShare` | **0–2%**（特例 3.1%） |
| 元素数 / `heavyShare` | 元素 ≥40；重元素占比低 |
| `primaryTypeRatio` | 相邻层级 **≥1.25×** 才算可读的步进 |
| 焦点唯一 | 与最大同级（±15% 内）的元件**只有 1 个** |
| 低对比文字 | 无描边的文字对底 **≥1.6:1**；有描边是合法处理 |
| `overflow` / `fontFallback` | **必须为 0。任何 fallback 都是缺陷** |
| 图层失败 | 任何 "layer failed" 都要读原因——报告看起来干净，可能少了一整个图层 |

### 12.3 工具本身的盲区（必须人工补）

**实测到的三个盲区，别把它们当成设计错误或设计通过：**

1. **静态对比度检查器看不见分层。** 它拿每个文字的颜色对 **ground** 算对比度。黑字压在黄带上（1:1 对底）会被报为"不可见"——**而它实际完全可读**。**它是平面检查器。**
2. **`heavyShare` / `meanOpacity` 测的是声明的图层不透明度，不是渲染后的对比度。** 用"接近底的色值"实现的淡，它读不出来。所以"高频低对比"要么用图层不透明度实现，要么接受这个指标读不出来。
3. **引擎对"已注册但缺该脚本字形"的字族不给警告。** 只对"未注册的字族"报错。**中文渲染成豆腐块可以是静默的。**

## 13. 我承认的边界

测量能带你到"正确"。**"精致"很难。**

以下这些测量到不了，必须由人决定，**不要在信息不足时用一个自信的猜测代替别人的判断**：

- 这个隐喻是否恰当。
- 这个品牌的性格是否适合它的受众。
- 这个构图是否真的愉悦，而不只是正确。
- 这个取舍（例如"失去世界感换阅读稳定"）在这个产品里是否值得。

**正确的做法是把工作组织成分工**：你按可验证的标准把结构和系统建到"正确"，**最终的美学判断交给拥有它的人**。
