# 平面设计 Agent 能力规格 · 实操简报

> 来源：一次真实任务（明日方舟美术视觉解析 PPT，28 页 + Photoshop 单页设计）的实测复盘。
> 所有结论都来自实际失败与验证，不是泛论。

---

## 0. 先明确一件最重要的事

**设计能力的瓶颈不在生成，在于「判断」和「验证」。**

实测结论（**已按后续复核修正**）：真正的环境限制只占约 **10%**；手法粗糙与归因错误占 **40%**；**审美与设计理解占 50%**。

> ⚠️ **修正记录**：本简报初版曾断言「Photoshop 自动化接口被裁剪，渐变 / 图层样式 / 剪贴蒙版 / 图层蒙版全都不可用，所以只能脚本搭骨架 + 人工补调子」。
> **该结论是错的。** 逐条复核后确认：那些「不可用」几乎全部是我的 **ExtendScript 写法错误**，不是 Photoshop 的能力边界。
> 这个误判本身成了本简报最有价值的一课 —— 详见**第 9 节**。

真正的环境瓶颈**不是能力，是速度** —— 见**第 3.5 节**，它直接决定工具选型与分工。

所以给新 Agent 的第一条建议是：**不要把预算全花在生成能力上，要花在「判断力」和「自检机制」上。**

## 1. 我需要什么工具（按缺口优先级排序）

### P0 —— 没有它就只能瞎猜

| 能力 | 为什么必需 | 具体缺口案例 |
|---|---|---|
| **同介质参考样本 + 度量提取** | 我给不出「好看的数值」，因为我不知道好看的具体值 | 参考图的网点最大半径、网格间距、强调色占比、明度区间——我全是估的 |
| **编辑级调子分析（带空间信息）** | 设计本质是调子的空间分布，不是一个平均色 | 参考图「左侧网格淡出、人物处淡入」，我只做到了「铺满」 |
| **文字排版的真实引擎** | 我的宽度估算是按字符分类给 em 值累加（CJK=1.0、大写=0.64…），和真实换行差 20–40% | 因此我不敢做精细排版，只能写保守的大框 |
| **自身几何输出的自检工具** | 我无法「看」，只能靠数字重建 | 曾把 custGeom 的局部坐标误当绝对坐标，整页形状全画错位置 |

**这四项的共同点：它们让我从「猜」变成「量」。**

### P1 —— 有它能少走很多弯路

- **目标格式的应用级渲染器**（PowerPoint / Keynote / InDesign 的真实导出），而不是第三方近似渲染
- **画布级渲染器**（不依赖目标应用"能否打开"），用于快速迭代
- **字体能力查询**：有哪些字重/字形、字距调整表、可变字体轴
- **色彩管理**：sRGB / Display P3、ICC 变换、色域检查

### P2 —— 顺手的部分

- **矢量图形库**（SVG 生成、布尔运算、路径简化）
- **位图工具**（重采样质量、双色调、半调图案、蒙版合成）
- **PSD / ODS 等分层格式读写**（便于人工接手）
- **批量变体生成**（同一设计跑多组参数对比）

### 一个反直觉的建议

**别给「图形生成 DSL」，给「能验证输出的工具」。**

我这次失败最多的不是"画不出来"，而是"画出来了但不知道对不对"。一个 `verify(render, spec)` 工具比十个 `drawCylinder()` 有用得多。

**具体该有的验证器：**

1. **几何回读验证** —— 解析输出文件，把我的意图与实际写入比对。这次靠它抓出过三处坐标错误。
2. **调子覆盖验证** —— 渲染成掩码图，统计前景覆盖率是否等于我的目标。这次靠它抓出「遮罩层出错」。
3. **文字溢出验证** —— 用真实字体度量检测越界，而不是估值。
4. **视觉回读** —— 最终必须能「看」自己的稿子。**不能看的时候，我根本不知道该问什么问题。**

## 2. 怎么提升审美

### 核心洞见：审美差距主要不是「感受力」，是「关系判断力」

我这次的设计错误清单里，**六条全部是关系错误，不是元素错误**：

| 我做的 | 应该的 | 错误类型 |
|---|---|---|
| 主体占画布高度 90% | 约 60%，留呼吸 | **比例** |
| 几何色块不透明且巨大 | 极小、极淡、多层 | **权重** |
| 网格 24px 均匀铺满 | 稀疏、有选择、成体系 | **疏密** |
| 姓名用白色实心压在浅底 | 橄榄绿描边，是视觉主角 | **层级** |
| 网点当背景纹理铺满 | 当调子工具，局部过渡 | **质感理解** |
| 一级信息（名）被二级（职业）压住 | 主次分明 | **秩序** |

**没有一条是「颜色不好看」或「形状不美」。全部是关系。**

### 所以训练该这么做

**1. 建立「关系库」而不是「素材库」**

不要记"这个封面好看"，要记：
- 主标题高度 / 画布高度 = ？
- 强调色像素占比 = ？
- 明度分布区间 = ？（专业设计常压在一个很窄的区间里）
- 网格密度 = ？
- 元素数量 vs 平均不透明度 的反比关系 = ？

**关键规律（这次实测发现的）**：
> **参考图的复杂度来自「高频低对比」——元素极多但每一个都极淡。我做的是「低频高对比」——元素少而重，所以看起来笨。**

这一条规律比十张参考图有用。

**2. 强制「先意图后形式」**

每个设计动作前先回答三个问题：
- 这页要让读者**看到什么**（唯一焦点）
- 它要**被怎么读**（视线路径）
- 哪些元素是**次要的**（必须让位）

我这次开局直接写代码摆元素，从来没问过这三个问题。**这是最根本的方法错误。**

**3. 每轮渲染后做「减法自检」**

不是问"我要的元素出现了吗"，而是三连问：
- **删掉哪些元素，稿子会变好？**
- **视觉焦点是否唯一？找不到焦点就是错的。**
- **缩到 25% 看，层级还成立吗？**

**4. 找「错误示例」学习，不只是成功示例**

审美的下限比上限容易学。建立反模式清单（见第 4 节），比模仿好作品见效快。

**5. 承认一个硬边界**

**审美里有一部分是我无法从工具获得的：**「这个设计为什么让人愉悦」「这个品牌该用什么气质」「这个隐喻是否得体」。

这部分只能靠：
- 大量真实设计奖作品的**规则提取**（不是观感描述）
- 人类反馈的**模式归纳**（把单次反馈转成可复用规则）
- 以及**承认自己的天花板**

诚实的说法是：**我能逼近「正确」，很难达到「精妙」。** 对多数交付（规范、系统、企业物料）「正确」就够了；对需要「精妙」的场合，应该设计成**人机分工**。

## 3. 怎么理解设计

### 设计的本质是「约束下的决策」，不是「创造」

我这次犯的最大理解错误：**把设计当成"元素的丰富组合"**。

我数了参考图有几个三角形、有网点、有等宽标签，然后把这些特征搬过来。结果是一堆特征，不是一个设计。

**正确的理解路径：**

**第一层：功能** —— 这个版面要完成什么？
（让人 3 秒内知道这是什么 / 让读者按顺序读完 6 条 / 让品牌显得可靠）
> 这一步我从来没做过。

**第二层：层级** —— 信息按重要性排序，每个层级只能有一个焦点。
> 元素多不等于信息多；层级乱等于没有信息。

**第三层：关系** —— 各元素的比例、位置、对比度、间距。
> 这是「审美」的真正所在。

**第四层：形式** —— 具体用什么形状、颜色、字体。
> 我这次直接从第四层开始，所以做出了「有形式无设计」的东西。

### 一个可操作的检查：设计是否成立的四个问题

1. **删掉一半元素，信息是否仍完整？** —— 若仍是，那删掉的那半是装饰，该减。
2. **眯眼看，焦点是否唯一？** —— 多个焦点 = 没有焦点。
3. **去掉颜色，层级是否仍成立？** —— 靠颜色撑层级是最脆弱的设计。
4. **不看内容，版面本身是否已经传达出气质？** —— 这是"设计感"的定义。

### 关于「理解参考图」

正确的参考分析产出**不是描述**，而是**规格**：

```
错误产物：「这张图有网点、有橄榄绿、有几何元素、有等宽标签」
正确产物：「底色明度 96%，网点仅在 x∈[0.3,0.6] 区间以 22% 出现并渐变淡出，
          强调色占比 3.2%，几何元素 7 个、平均不透明度 18%、最大边长占画布 4%，
          网格间距 24px 但只覆盖 40% 画布面积，正文字号 15px，主标题 54px，
          零个完全圆角，细线统一 1px」
```

**前者是观感，后者是可执行约束。** 让新 Agent 学会产出后者。

## 3.5 迭代成本决定工具选型（**本节为修正后新增，优先级很高**）

这是初版完全漏掉、但比「能力边界」重要得多的一条约束。

### 实测数字

| 路径 | 单次迭代耗时 |
|---|---|
| **Photoshop COM 冷启动** | **40–60 秒 / 轮** |
| 本地渲染引擎（如 canvas） | **约 1 秒 / 稿** |

### 这条数字的推论

初版说「我做不出参考图的精细度是因为审美不够」。**主因其实是迭代带宽不够。**

- 每轮 PS 渲染 40–60 秒 + 写改脚本时间 ⇒ 实际 **1–2 分钟 / 轮**
- 若每页需 3–5 轮 ⇒ **每页 10 分钟左右**
- 而达到参考图那种精修度需要**几十轮** ⇒ **一小时以上纯等待**，且无法并行

**结论：不要拿 Photoshop 当迭代工具。** 正确分工是：

> **快速引擎负责迭代（≈1 秒/稿，跑几十轮收敛），Photoshop 只负责最终分层交付。**

初版给的「脚本搭骨架 + 人工补调子」是基于错误能力边界的错误分工；
正确分工是按**速度**切的，不是按**能力**切的。

## 4. 反模式清单（我实测踩过的坑，直接作为硬约束）

### 生成层面

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 在循环里复用同一图层改参数 | 只保留最后一次迭代 | 每个元素独立图层 |
| 用多层矩形模拟渐变 | 出现硬边、密度不均 | 用**真实渐变**（`contentLayer + gradientForm`）；不要再近似 |
| **试一次就判「不支持」** | 归因错误，放弃可行路径 | **≥2 种标准写法都失败才可判定** |
| **混淆「命令不存在」与「参数无效」** | 报错已给出答案却被读反 | 按 9.2 节判别表处理：参数无效 ⇒ 改描述符，不换方案 |
| 把「自检失败」当「功能不支持」 | 归因错误，放弃正确路径 | 至少尝试 2 种标准写法再判定 |
| 边搭边发现 API 失败 | 中途打补丁，破坏设计一致性 | **先建已验证手法库，再组合** |
| 没隔离测试单个元素 | 错误混在整体里看不见 | 关键层单独渲染一次 |
| 一次性生成 N 页 | 错误被复制 N 次 | **验证闭环后再铺量** |
| 拿慢工具做迭代 | 40–60 秒/轮，几十轮就崩盘 | **按速度选工具**：快速引擎迭代，慢工具只做最终交付 |

### 设计层面

| 反模式 | 正确做法 |
|---|---|
| 主体占画布比例过大（>70%） | 50–65%，留呼吸空间 |
| 每个元素都重（高不透明度/高对比） | 高频低对比：元素多而极淡 |
| 网格/纹理均匀铺满 | 局部出现、渐变过渡、有选择 |
| 元素数量少但每个都大 | 层次来自数量与淡度的组合 |
| 强调色大面积使用 | 强调色占比 ≤5% |
| 把最重的字重给最不重要的信息 | 字阶严格对应信息层级 |
| 用颜色承担层级 | 用尺寸、字重、位置承担；颜色是锦上添花 |
| 文字退化成"背景色同色" | 浅底上不要用白色实心字 |

### 流程层面

| 反模式 | 正确做法 |
|---|---|
| 先写代码摆元素 | **先回答功能/层级/焦点三问** |
| 铺量后才做视觉验证 | 单页验证闭环后再铺 |
| 只问"元素出现了吗" | 问"这看起来像被设计过的版面吗" |
| 无人反馈下迭代多轮 | 每 2–3 轮必须拿人类反馈 |

## 5. 建议的工作流（已验证）

```
0. 能力侦察
   └─ 目标格式能否嵌入位图？渲染路径是否可用？⇒ 最小用例验证，1 页
1. 参考分析
   └─ 提取规格（色值/占比/明度区间/尺度级数/网格密度/元素数与淡度）
2. 意图声明
   └─ 写下：唯一焦点 / 阅读路径 / 次要元素清单
3. 手法库建设
   └─ 把每个要用到的 API 逐个验证成可复用函数（不通过就换方案）
4. 单页构建 → 渲染 → 视觉自检（四问）→ 修正
   └─ 通常需要 3–5 轮
5. 人类确认
   └─ 拿到反馈，把反馈转成规则，而不是只改这一页
6. 规格化铺量
   └─ 把验证过的设计固化成参数，批量生成
7. 分层交付
   └─ PSD/源文件 + 渲染图 + 手法库脚本
```

**第 0 步和第 3 步是我这次完全跳过、代价最大的两处。**

## 6. Photoshop 脚本手法（**已修正，全部可用**）

> ⚠️ 本节初版把一批**写法错误**误判为「能力缺失」，导致得出「只能人机分工」的错误架构结论。
> 下表左列是初版的错误结论，右列是复核后的真相。**务必按下表右侧写法执行。**

### 6.1 曾经误判为「不可用」的，其实都是写法问题

| 初版错误结论 | 真相（正确写法） |
|---|---|
| 文字颜色不可用 | 用 `SolidColor` 正常 —— 错的是 `RGBColor` |
| 调整层不可用 | 用 `Usng + contentLayer` 正常 —— 错的是 `adjustmentLayer` |
| 图层蒙版 / 剪贴蒙版不可用 | `Mk + Chnl1 + UserMaskEnabled` / `groupEvent + setd` 正常 |
| **渐变填充不可用** | `contentLayer + gradientForm + 色标列表` 正常 |
| `halftonePattern` 不可用 | 它**仅灰度文档可用**；RGB 文档应改用 `colorHalftone` |

**渐变那条最值得记住**：当时 Photoshop 报的原话是「**命令"填充"的参数当前是无效的**」——
它清楚地说了是**参数无效**，不是命令不存在。**报错已经把答案给我了，我读错了。**

### 6.2 实测确认可用的能力

- `DoJavaScript` 走 COM 驱动，**无需 GUI**
- **图层**：栅格层、文字层、图层组、独立不透明度、混合模式（MULTIPLY / OVERLAY / SCREEN 等）
- **文字**：字体（用 `postScriptName`）、字号、**字距 tracking**、颜色、位置、旋转
- **图层蒙版 / 剪贴蒙版**：`Mk + Chnl1 + UserMaskEnabled`；`groupEvent + setd`
- **渐变**：`contentLayer + gradientForm` + 色标列表
- **调整层**：`Mk` + `Usng + contentLayer`
- **调整（栅格层上直接执行）**：`HStr` 色相饱和度、`desaturate` 去色、`curves` 曲线
- **滤镜**：高斯模糊、USM、High Pass、Minimum、Maximum、`colorHalftone`（网点）
- **智能对象**：`Plc` 置入 + `Trnf` 精确缩放位移
  - 陷阱：`scale` **单独传参不生效**，必须与 offset 合并进**同一个 transform 事务**
- **导出**：PNG、**分层 PSD**

### 6.3 关于 `rasterizeLayer`

初版把它列为「不可用」。它确实在部分上下文里报「命令"栅格化"当前不可用」，
但注意：**报错说"当前不可用"意味着命令被识别、只是执行上下文不对**——
这与「命令不存在」是两回事（对比 9.2 节的判别法）。
遇到它应先检查图层种类与文档模式，而不是直接换方案。

## 7. 给新 Agent 的定位建议

基于修正后的数据，定位应该是：

**做「结构与系统」的专家，并在速度允许时逼近「调子与精妙」。**

- ✅ **擅长**：栅格系统、尺度级数、字阶、色彩系统、组件库、多页一致性、批量变体、可编辑分层文件
- ✅ **也能做**（在快速引擎上迭代足够轮次的前提下）：调子过渡、渐变、材质融合、视觉精修
- ⚠️ **限制点不是能力而是速度**：凡需几十轮微调的场合，必须在快速引擎上做，不能走 COM
- ❌ **仍不擅长**：需要「精妙感」的单一视觉焦点作品 —— 这是判断力问题，与工具无关

**并且必须内建：**
1. **单页验证闭环**（不验证不铺量 —— 初版正是因为跳过它，把 22 页建在坏掉的核心能力上）
2. **视觉回读能力**（不能看图就等于盲人设计）
3. **参考规格提取**（把观感转成数值，而不是特征清单）
4. **先算迭代成本再选工具**（第 3.5 节）
5. **判别「命令不存在」与「参数无效」**（第 9.2 节）
6. **主动求助机制**（连续 2 轮无进展就交给人）

## 8. 一句话总结

> **修正后的比例：环境约 10%、手法与归因错误约 40%、审美与理解约 50%。**
>
> 而「环境那 10%」不是能力缺失，是 **COM 冷启动 40–60 秒/轮的速度限制** ——
> 它决定的是**工具选型**，不是**能不能做**。
>
> **真正拖垮交付的是那 40%：把写法错误当成能力边界，
> 用一次失败的试错换来了一个错误的架构结论。**
>
> 所以给新 Agent 最重要的不是更强的生成工具，
> 而是 **能看、能量、能判断自己做得对不对** 的能力，
> 以及 **在动手之前先想清楚"这页要让读者看到什么"** 的纪律。

---

## 9. 最重要的一课：把「我没写对」说成「它不支持」

本节是整份简报里最该被继承的部分。它不是关于设计，是关于**如何在给他人结论前保持诚实**。

### 9.1 事故经过

我在实测中遇到若干 Photoshop 命令报错，**每个只试了一种写法**，然后把结果写成：

> 「Photoshop 的自动化接口在本环境下被裁剪了 —— 渐变、图层样式、剪贴蒙版、图层蒙版全都不可用，
> 所以只能『脚本搭骨架 + 人工在 GUI 补调子』。」

这是一条**写进交付文档、被他人当作架构依据的结论**。而它的依据是每个 API 试了一次。

后续复核发现：**几乎全部是写法错误。** 正确写法见第 6.1 节表格。

### 9.2 判别法：一句话分清「命令不存在」与「参数无效」

这是本次最有价值的可复用技能，**成本极低但价值极高**：

| 报错措辞 | 含义 | 该做什么 |
|---|---|---|
| 「命令 **X 当前不可用**」 | 命令**被识别**，但执行上下文不对 | 检查图层种类 / 文档模式 / 选区状态 |
| 「命令 **不存在** / 未知的」 | 命令名可能写错，或真的没这个 API | 查 charID，或换等价命令 |
| 「**参数当前是无效的**」 | **命令在，描述符结构错了** | **改描述符，不要换方案** |
| 「程序错误 / 内部错误」 | 描述符缺必需字段或嵌套层级错 | 补齐字段，参考官方 ActionDescriptor 结构 |

**当时渐变报的就是「参数当前是无效的」** —— 答案已经写在报错里，我读成了「不支持」。

### 9.3 教训：同一件事，我在两个工具上用了两种严谨度

**PowerPoint 那边我做对了**：`addImage` 生成的文件打不开时，我没有下结论，而是
逐层深挖 —— 试了 JSZip / .NET ZipArchive / 手工 OOXML / COM 四条路径，
最终抓出两个真实缺陷（`[Content_Types].xml` 缺 png 声明、`<a:blip>` 空元素非法）。

**Photoshop 那边我做错了**：同样的情况，每个 API 试一次就判定「不支持」。

**同一个我，同一类问题，两种做法。** 所以这不是能力缺口，是**执行不一致** ——
而「先建已验证手法库」本来就是我写进第 5 节工作流的纪律，我自己没执行。

### 9.4 可强制执行的规则（建议写进新 Agent 的系统提示）

1. **任何「不支持 / 不可用 / 能力缺失」的结论，必须建立在该命令 ≥2 种标准写法都失败的基础上。**
2. **先读报错语义，再决定行动**（用 9.2 节的判别表）。
3. **在隔离环境单独验证可疑命令**，不要在完整设计里试 —— 混在整体里看不见。
4. **把「我没试通」和「这条路不通」严格分开表述。**
   前者是可修的个人失误，后者会让他人放弃本来可行的路径。
5. **在给他人做架构建议前，先问：这个结论如果错了，对方会损失什么？**
   本次的代价是：基于错误结论提出了错误的人机分工方案。

### 9.5 这条教训的通用形式

> **试错失败时，默认假设是「我写错了」，而不是「它不支持」。**
> 只有当多种标准写法都失败、且报错语义指向「不存在」时，
> 才允许升级为能力边界的结论 —— 并且要在结论里写清验证过程。

这条不只适用于 Photoshop，适用于一切与外部系统交互的场合。
