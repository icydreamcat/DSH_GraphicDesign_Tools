# 规则 · 索引

> **这里放什么**：**纯结论与规则**，按内容分类。名前是规则的名字，不是它出自哪个案例。
> 每一份都不讲"怎么得来的、曾经错在哪"——那些属于案例文献与本地记录。
>
> **案例文献在哪**：拆解过程、实测数据、被推翻的说法、置信度分级，都在**本地库**
> （`knowledge/reference/`）。它们是阅读材料，用来随手翻阅、用来核验一条规则的证据；
> **规则来自它们，但规则不该被埋在它们里面。**
>
> **判据一句话**：一份文档读完能**直接照着做**，它进这里；读完只让人知道
> "当时发生过什么、谁怎么做的"，它不进。

## 三类内容各自的家

这套东西散在三处，是因为它们的**用途不同**，而不是因为随手放的：

| 内容 | 家 | 为什么 |
|---|---|---|
| **规则**（纯结论，直接照做） | **这里**（进仓库） | 新克隆的人与下游都要能直接读 |
| **案例文献**（拆解过程、实测、置信度、被推翻的说法） | 本地库 `knowledge/reference/` | 是阅读材料与证据，不是执行件；体量大，且是别人的作品数据 |
| **过程记录**（某一轮做了什么、坏了什么） | 本地库 `knowledge/agent/` 与 `tooling/` | 本机与环境前提，换机器即失效 |

**一条边界**：案例文献里"我上一版以为 X、实测否定了"这类话**必须留着**——
它是一条结论唯一能证明自己来自实测、而不是来自既有印象的证据。
但它是**证据**，所以留在案例里；**规则文件里只写"X 不成立"，不写谁曾经以为 X。**

## 写一份规则文件的规矩

1. **结论与规则，不带过程。** 不出现"本地发生了什么、做过什么实验、上一版怎么想"。
2. **每条规则要能被执行。** 带判据、数值、或可判定的条件；"要注意整体性"这类不算规则。
3. **承认边界。** 测量到不了的地方（隐喻是否贴切、是否真的好）要写明它到不了，并交给作品的所有者。
4. **禁止清单要有。** 每份规则末尾列出会犯的错；错误比正确更容易被记住。
5. **不重复。** 一条规则只在一个文件里定义；其它文件引用它。
